## T0-4 지연 누적 (latency.py, 프레임마다 처리 0.2초, 2분)
지연 = (시작 후 지난 실제 시간) − (시작 후 지난 프레임 시각, CAP_PROP_POS_MSEC = V4L2 버퍼 타임스탬프)

| 날짜 | 입력 | 방식 | 처리한 FPS | 지연 처음 10초 | 지연 마지막 10초 | 최대 | 판정 |
|---|---|---|---|---|---|---|---|
| 10-29 09:13 | 웹캠 720p 30fps | (a) read() 그대로 | 4.43 | 742 ms | 860 ms | 876 ms | 지연 큼 |
| 10-29 09:15 | 웹캠 720p 30fps | (b) 최신 1장 리더 | 4.92 | 7 ms | 36 ms | 46 ms | 합격 |
| 10-29 10:29 | IP 카메라 stream2 848x480 25fps | (a) read() 그대로 | 약 3 | - | 약 105 s (화면 시계 10:27:14 vs 실제 10:29:02) | 계속 증가 | 지연 누적 |
| 10-29 10:33 | IP 카메라 stream1 2560x1440 25fps | (a) read() 그대로 | 약 3 | - | 약 106 s (화면 시계 10:31:20 vs 실제 10:33:06) | 계속 증가 | 지연 누적 |
| 10-29 10:3x | IP 카메라 | (b) 최신 1장 리더 | 약 3 | 1–2 s 이내* | 1–2 s 이내* | 2 s 미만 | 합격 |

- (a): 시작 1초 만에 지연이 약 0.8초로 뛰고 2분 내내 0.82~0.88초에 머묾. 웹캠은 드라이버 버퍼가 4장 정도라, read()가 0.2초마다 가장 오래된 1장을 꺼내 "4장 × 0.2초 ≈ 0.8초" 뒤처진 상태로 고정된다(버퍼가 꽉 차면 새 프레임은 버려짐). 그래서 웹캠은 무한히 쌓이지는 않지만 늘 0.8초 늦은 화면을 본다.
- (b): 스레드가 30fps로 계속 비우고 최신 1장만 남겨, 처리 시점의 프레임이 최대 46ms 이내로 신선. 처리량도 4.92fps로 (a)보다 높음(버퍼에서 꺼내는 시간이 없음).
- (a)·(b) 차이 2분 뒤 약 0.82초. RTSP는 소켓·디코더 버퍼가 커서 (a)에서 지연이 계속 커질 것으로 예상 → IP 카메라로 확인 예정.
- 스냅샷: runs/latency_{a,b}_webcam720_t0.jpg, _t120.jpg
- IP 카메라 지연은 카메라가 영상에 찍는 시계(OSD, 1초 단위)와 젯슨 시계(스냅샷 저장 시각)의 차이로 셈. (a)는 120초 동안 약 14–16초 분량의 프레임만 처리 → 마지막 처리 프레임의 화면 시각이 10:27:14인데 실제 시각 10:29:02 (stream2), 10:31:20 vs 10:33:06 (stream1) → 약 1분 45초 늦음. 웹캠과 달리 FFmpeg RTSP는 받은 프레임을 버리지 않고 모두 쌓아 두므로 지연이 시간에 비례해 계속 커짐 (2분 뒤 약 0.88초/초 비율).
- (b)는 화면 시각과 실제 시각 차이가 1–2초 안 (카메라 인코딩·전송·복원 지연 + 카메라 시계 오차 포함, 1초 단위라 더 정밀하게는 T0-6 glass-to-glass로 잴 예정).
- *(b)의 IP 카메라 지연은 카메라 OSD 시계(1초 단위) 기준이라 1–2 s로만 표기. 정밀 값은 T0-6 (약 0.5 s).
- *POS_MSEC 기준 값: RTSP는 스트림 시각이라 처음 프레임 대비 상대값만 의미 있음 (stream1은 음수가 나와 사용 안 함).
- 결론: (a)와 (b)의 2분 뒤 차이 — 웹캠 약 0.8초, IP 카메라 약 103초. 원인은 수신 버퍼 크기: 웹캠 드라이버는 4장만 두고 넘치면 버리지만, RTSP/FFmpeg는 TCP·디코더 버퍼에 계속 쌓아 두어 처리 속도(약 3fps) < 카메라(25fps)이면 끝없이 밀림.

- 개선 여지: 웹캠은 장치 파일이 다시 생기는지 0.5초마다 확인해 바로 열면 꽂은 뒤 1초 안팎으로 줄일 수 있음.

## T0-6 glass-to-glass (IP 카메라 → 젯슨 → Mac Chrome)
방법: Mac에 /clock(밀리초 시계)과 뷰어를 나란히 띄우고 IP 카메라가 시계 창을 찍게 함. Mac 화면 캡처(Cmd+Shift+3) 한 장에 두 값이 같이 찍히므로 지연 = 진짜 시계 − 뷰어 속 시계. 경로: 카메라 H.265 인코딩 → RTSP/TCP → 젯슨 FFmpeg 복원 → JPEG 인코딩 → MJPEG/HTTP(Tailscale) → Chrome 표시.

- 릴레이 경유 6장: 평균 514 ms, 최소 467, 최대 550 (편차 ±40 ms ≈ 카메라 25fps 한 프레임 40 ms). 화면 속 화면(재귀)에 찍힌 한 단계 안쪽 시계끼리의 차이도 500–534 ms로 같은 값을 줌.
- 원본(:8020) 1장 680 ms. 릴레이는 젯슨에서 복원·재인코딩을 한 번 더 하지만 보낼 데이터가 1/4이라 전송·브라우저 복원이 빨라 오히려 짧게 나옴 → 지연의 상당 부분이 큰 JPEG의 네트워크 전송·브라우저 복원.
- :8020 원본은 Mac으로 약 12 MB/s(≈100 Mbps)를 보내 Wi‑Fi/Tailscale이 잠깐 밀리면 Chrome에서 검은 화면이 됨 → t0/relay.py(:8030, RTSP 새로 열지 않음)로 해결.
- 판정: 합격 (약 0.5초, 모니터링 용도로 충분). 더 줄이려면 서브 스트림(848x480) 사용, 또는 MJPEG 대신 H.264 그대로 전달(WebRTC 등).

## 2. 지연 측정표

### 리더 방식별 2분 뒤 지연 (T0-4, 처리 지연 0.2 s를 넣음)

| 입력 | (a) `read()` 단순 반복 | (b) 최신 1장 리더 |
|---|---|---|
| 웹캠 | 약 0.8 s, 일정 | 7~46 ms |
| IP 카메라 | 계속 늘어서 2분 뒤 약 105 s 밀림 | 1~2 s 이내, 늘지 않음 |

원인:
- (a)는 읽지 못한 프레임이 버퍼에 쌓인다. 카메라는 25~30 fps로 보내는데 루프는 약 5 fps로만 꺼낸다.
- 웹캠은 V4L2 드라이버 버퍼가 약 4장이라, 그 이상 쌓이지 않고 지연이 약 0.8 s에서 멈춘다.
- RTSP는 FFmpeg와 TCP 버퍼가 사실상 무제한이라 지연이 계속 커진다.
- (b)는 별도 스레드가 계속 읽고 최신 1장만 남긴다. 그래서 처리 속도와 상관없이 지연이 늘지 않는다.

### 화면→화면 지연 (T0-6, 맥북 밀리초 시계를 카메라로 찍어 화면 캡처로 비교)

| 입력 | 표시 경로 | 지연 | 표본 |
|---|---|---|---|
| 웹캠 직접 (V4L2) | 젯슨 MJPEG, Tailscale, Chrome | **약 0.18 s** (0.17~0.20) | 6장 |
| IP 카메라 RTSP | 원본 2560x1440 MJPEG, Chrome | 0.68 s | 1장 |
| IP 카메라 RTSP | 1280폭 q70로 줄여서 다시 보냄 (relay) | **0.51 s** (0.47~0.55) | 6장 |

- 웹캠과 IP의 차이 약 0.33 s는 IP 카메라 쪽 과정에서 생긴다. 카메라가 H.265로 압축하고 버퍼링한 뒤, RTSP로 받아서 FFmpeg가 다시 푼다.
- 원본 화면이 줄인 화면보다 오히려 느렸다. 장당 480 KB × 25 fps를 보내느라 전송과 브라우저 복원이 늦어졌고, 이 때문에 검은 화면이 자주 생겼다. 지연의 상당 부분이 큰 JPEG 전송이라는 뜻이다.

## 3. 재연결 (T0-5): 프로세스 재시작 없이 복구

| 입력 | 방법 | 끊김 감지 | 다시 꽂은 뒤 복구 | 재연결 | 판정 |
|---|---|---|---|---|---|
| 웹캠 | USB를 약 10 s 뽑음 | 0.17 s (장치 파일이 사라짐) | 8 s 이내 (재시도 간격이 최대 8 s) | 1회 | 합격 |
| IP 카메라 | 랜선을 약 40 s 뽑음 | 30 s (FFmpeg 기본 타임아웃) | 약 17 s | 1회 | 합격 |

- 개선: IP 쪽은 TCP 연결이 바로 끊기지 않아서 감지가 늦었다.
- 그래서 `camlib`에서 FFmpeg 읽기 타임아웃을 3 s로 줄이고, RTSP는 읽기 실패 2번이면 바로 다시 열게 했다.
- 14:03에 적용했다.
- 14:08에 다시 시험했다.

| | 수정 전 (13:52) | 수정 후 (14:08) |
|---|---|---|
| 끊김 첫 감지 | 30 s | 3 s |
| 끊김 판정, 다시 열기 시작 | 57 s | 12 s |
| 전체 끊긴 시간 | 약 58 s | 약 32 s (대부분 랜선을 빼 둔 시간) |
| 재연결 / 프로세스 | 1회 / 유지 | 1회 / 유지 |

판정이 3 s가 아니라 12 s 걸린 이유가 있다. 끊기는 중에 조각난 프레임이 몇 장 들어오면서 실패 횟수가 초기화됐다.

## 확인 문제 1

**1-1.** `appsink drop=true max-buffers=1 sync=false`

- `drop=true`: 큐가 차면 위쪽 파이프라인을 막지 않고 가장 오래된 버퍼를 버린다.
- `max-buffers=1`: appsink 큐에 최대 1장만 둔다. 그래서 앱이 꺼내는 것은 항상 최신 프레임이다.
- `sync=false`: 버퍼의 타임스탬프와 파이프라인 시계를 맞추느라 기다리지 않는다. 디코딩되는 즉시 넘긴다.

세 옵션을 합치면 우리가 만든 "최신 1장 리더"(T0-4 (b))를 GStreamer 안에서 하는 것과 같다.

**1-2.** RTSP 전송을 UDP에서 TCP로 바꾸면

- **좋아지는 점**
  - 패킷이 사라지지 않는다. 그래서 회색 번짐이나 블록 깨짐 같은 화면 손상이 없다.
  - 방화벽, NAT, VPN(Tailscale)을 잘 통과한다. 이미 연 RTSP 연결 하나에 영상을 함께 실어 보내기 때문이다.
- **나빠지는 점**
  - 잃은 패킷을 다시 보내느라 기다린다. 이때 뒤 패킷까지 줄줄이 막힌다(head-of-line blocking).
  - 그래서 네트워크가 흔들리면 지연이 튀고 버퍼가 쌓인다.
  - 연결이 끊긴 것을 늦게 안다. 이번 T0-5에서 기본 30 s가 걸린 것이 그 예다.
  - 헤더와 ACK 때문에 데이터가 조금 더 든다.

## 생각해 볼 점

- **30 fps 입력, 10 fps 추론:**
  - 1초에 20장, 1분에 1,200장을 버려야 한다.
  - 버리지 않으면 큐가 1초에 20장씩 늘어난다. 1분 뒤에는 결과가 약 40 s 늦어지고 메모리도 계속 는다. T0-4 (a)의 IP 결과(2분 뒤 105 s)가 바로 이 현상이다.
- **메인 스트림이냐 서브 스트림이냐:**
  - 기본은 서브 스트림(848x480)이 맞다. CPU 8 %로 메인(54 %)의 약 1/6이고, 가까운 사람을 검출하기에는 충분하다.
  - 재실 인원처럼 먼 사람까지 세야 하면 사람이 몇 픽셀밖에 안 된다. 이때는 메인 스트림을 쓰되 관심 영역을 잘라 쓰거나, 낮은 빈도(예: 1~2 fps)로 돌린다. 디코딩은 NVDEC로 넘겨 CPU 부담을 줄인다.
- **NVENC가 없다는 것:**
  - 디코딩은 하드웨어(NVDEC)로 할 수 있다.
  - 하지만 다시 인코딩하는 일은 전부 CPU가 한다. 브라우저로 보내는 MJPEG, RTSP 재송출, 녹화가 여기에 들어간다.
  - 그래서 보내는 영상은 작게 줄이고(이번 relay처럼 1/4), 필요할 때만 보낸다. 평소에는 영상 대신 검출 결과(이벤트, 메타데이터)를 MQTT로 보내는 구조가 맞다.

## 심화 (B)

### B1. NVDEC 하드웨어 디코딩과 CPU 디코딩 비교

입력:
- IP 카메라 강의실 화면 60 s를 1080p 25 fps로 줄인 H.264 영상과 H.265 영상 (각 1,531장)
- IP 카메라 RTSP 원본 (H.265 2560x1440)

디코더:
- HW: GStreamer `nvv4l2decoder`
- FF: OpenCV FFmpeg (CPU)
- de265: GStreamer `libde265dec` (CPU)

모두 BGR 프레임까지 만든 기준이다. 결과는 젯슨 `~/eg2-lab/applab/runs/b1_decode.md`에 있다.

실시간 25 fps에서 쓴 CPU (코어 1개 = 100 %):

| 입력 | HW (NVDEC) | FF (CPU) | de265 (CPU) |
|---|---|---|---|
| 1080p H.264 | 10 % | 44 % | — |
| 1080p H.265 | 10 % | 53 % | 127 % |
| RTSP 1440p H.265 | 15 % | 56 % | 123 % (24.7 fps, 겨우 따라감) |

최대 속도:

| 입력 | HW | FF | de265 |
|---|---|---|---|
| 1080p H.264 | 169 fps / CPU 57 % | 196 fps / CPU 279 % | — |
| 1080p H.265 | 164 fps / CPU 58 % | 135 fps / CPU 241 % | 42 fps / CPU 193 % |

해석:
- 같은 25 fps를 낼 때 NVDEC은 CPU를 FFmpeg의 1/4~1/5만 쓴다(1080p 약 0.1코어). 남는 CPU를 추론 전·후처리에 쓸 수 있다.
- HW의 최대 속도는 코덱과 상관없이 약 165 fps다. 한계는 NVDEC이 아니라 BGR 변환과 메모리 복사 쪽이다.
- FFmpeg는 H.264에서 196 fps로 더 빠르지만 6코어를 거의 다 쓴다(시스템 CPU 86 %).
- H.265를 CPU로 풀면 H.264보다 무겁다. libde265는 FFmpeg보다 약 2.5배 느리다.
- 측정 중에 뷰어 2개가 같이 돌아서 시스템 CPU의 바닥값이 약 45 %였다. 표의 값은 측정 프로세스만 따로 잰 값이라 비교에는 문제없다.
- `~/eg2`의 OpenCV 5.0은 GStreamer 없이 빌드됐다. 그래서 `cv2.VideoCapture(..., CAP_GSTREAMER)`로는 NVDEC을 쓸 수 없다. NVDEC을 쓰려면 GStreamer appsink(`gi`)로 프레임을 받아야 한다.
### B2. Linux 웹캠을 RTSP로 송출해 보드에서 실시간 추론

macOS용 `fake_camera.sh webcam`을 Linux로 옮겼다. Linux PC는 젯슨 자체를 썼다. 송신과 수신이 같은 보드에서 돈다.

구성:
- 코너 웹캠
- → `b2/fake_camera_linux.sh`: x264 zerolatency H.264 2 Mbps로 압축하고, 끊기면 2 s 뒤 자동으로 다시 시작한다.
- → MediaMTX v1.21.2: 젯슨 내부(127.0.0.1)에서만 접근된다. RTMP로 받아 RTSP로 내보낸다.
- → `rtsp://127.0.0.1:8554/live/webcam`
- → `b2/rtsp_infer.py`: 최신 1장 리더로 받고, YOLO11n GPU FP16으로 사람을 검출한다.
- → 브라우저 화면 `:8030`

RTSP 송신을 RTMP 입력으로 우회한 이유가 있다. 젯슨의 ffmpeg는 기능이 빠진 축소판이고, GStreamer에도 RTSP 송신 모듈(rtspclientsink)이 없다.

30 s 측정:

| 항목 | 값 |
|---|---|
| RTSP 수신 fps | 29.9 |
| 검출 처리 fps | 24.9 |
| 추론 시간 | 33 ms |
| 프레임 나이 (받은 뒤 결과까지) | 50 ms, 일정함 (밀리지 않음) |
| CPU: 송신 / MediaMTX / 수신 | 56 % / 1 % / 109 % |
| GPU 평균 | 14 % |

검출 기준값(conf) 조정 (16:55, 각 60 s, 웹캠 각도는 고정):

| conf | 평균 사람 수 (최소~최대) | 처리 fps | 추론 |
|---|---|---|---|
| 0.4 | 5.2 (3~8) | 21.7 | 37 ms |
| 0.3 | 6.0 (4~8) | 22.7 | 35 ms |

- 0.3으로 낮추니 약 15 % 더 잡았고, 속도는 같다.
- 모니터에 가려 놓치던 사람도 잡혔다.
- 오검출이 1건 생겼다. 한 사람에게 박스가 2개 겹쳐 그려졌다.
- 모니터 뒤로 머리만 보이거나 화면 끝에 손만 보이는 사람은 여전히 못 잡는다. 이건 카메라 위치의 한계다.

결과는 젯슨 `~/eg2-lab/applab/runs/b2_rtsp.md`에 있다.

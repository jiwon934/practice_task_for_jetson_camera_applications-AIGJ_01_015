## 1. 무엇을 해결하나 (A1 + A4)

**현장 문제**
- 3강의실은 CO₂가 1,500 ppm을 넘어야 환기하고, 냉난방은 사람이 없어도 켜져 있다.
- 강의실 장비 앞 통로에서는 사람이 너무 가까이 다가와도 알려 줄 수단이 없다.
- 보드 한 대가 IP 카메라로 **재실 인원(A1)** 을 계속 세고, 웹캠 2대(스테레오)로 장비 앞 **근접 경고(A4)** 를 낸다.
- 결과는 숫자와 상태로만 내보낸다.
  - 냉난방·환기 제어, 다른 팀 대시보드, 로컬 LLM 에이전트는 MQTT나 REST로 그 값을 가져다 쓴다.
  - 영상은 보드 밖으로 나가지 않는다.

**구성**

| 부분 | 카메라 | 처리 |
|---|---|---|
| A1 재실 인원 | IP 카메라 VIGI C540-W, RTSP stream1 (2560x1440), 높은 곳에서 좌석 줄을 내려다봄 | YOLO11n TensorRT FP16 960, 2x2 타일, 포함 억제 0.6, 구역(정원 40), 발 기준, 10 s median, 5 fps |
| A4 근접 경고 | C920 2대, USB by-path 2.4(왼쪽)/2.2(오른쪽), 기준선 127 mm, 과제 5 보정 | YOLO11n TensorRT FP16 640 (사람) + OpenCV StereoSGBM (CPU, 640x360), 몸통 영역 중앙값 거리, 8 fps |

- 한 프로세스, 한 CUDA 컨텍스트 안에 엔진 두 개를 올렸다.
- 카메라마다 읽기 스레드가 따로 있어, 한 대가 끊겨도 다른 처리는 계속된다.

## 2. 결과 형식 문서 (다른 팀용)

**접속**
- MQTT 브로커: 젯슨 `:1883` (팀 공용, 발행만 함)
- REST: `http://100.105.144.42:8030` (Tailscale)
- 모든 MQTT 메시지는 **qos 1, retain** 이다. 새 구독자도 접속하자마자 현재값을 받는다.
- 시각 `ts`는 Unix 초(UTC 기준 epoch, 소수점 ms)다.

### 2.1 MQTT 토픽

| 토픽 | 언제 보내나 | 내용 |
|---|---|---|
| `jiwon934/t6/occupancy` | 인원(count)이 바뀔 때 + 10초마다 | 재실 인원 |
| `jiwon934/t6/proximity` | 상태가 바뀔 때 + 60초마다 | 근접 상태 |
| `jiwon934/t6/status/service` | 시작할 때 online, 죽으면 LWT로 offline | 서비스 생존 |
| `jiwon934/t6/status/ipcam`, `/left`, `/right` | online/offline이 바뀔 때 | 카메라별 연결 |

**occupancy 예시**
```json
{"ts":1793347813.281,"room":"applab-classroom","count":4,"raw":4,
 "zones":{"rear":1,"middle":3,"near":0},"capacity":40,"window_s":10}
```

| 필드 | 단위 | 뜻 |
|---|---|---|
| count | 명 | 최근 10초 raw의 중앙값. **제어에는 이 값을 쓴다** |
| raw | 명 | 이번 프레임에서 센 수 (흔들림 있음, 진단용) |
| zones | 명 | 구역별 raw (rear 뒷줄, middle 가운데, near 앞쪽) |
| capacity | 명 | 정원 |
| window_s | 초 | 평활 창 길이 |

**proximity 예시**
```json
{"ts":1793347790.833,"state":"none","nearest_m":null,"people":0,
 "near_m":1.0,"far_m":3.0,"reason":"사람 없음"}
```

| 필드 | 단위 | 뜻 |
|---|---|---|
| state | — | near(< 1.0 m), mid(1.0~3.0 m), far(> 3.0 m), none(사람 없음), unknown(측정 불가 또는 웹캠 끊김) |
| nearest_m | m | 가장 가까운 사람까지 거리 (1초 중앙값). 없으면 null |
| people | 명 | 스테레오 화면 안 사람 수 |
| near_m, far_m | m | 경계값 |
| reason | — | none·unknown일 때 이유. 예: "사람 없음", "웹캠 없음/끊김", "무늬 부족" |

상태 전환 규칙은 다음과 같다.
- 경계에 ±0.1 m 히스테리시스를 둔다.
- 새 상태가 **2초 이상** 이어져야 바꾼다.
- 웹캠 끊김은 즉시 unknown으로 바꾼다.

**status 예시**
- `{"state":"online","ts":1793346881.924}`
- service 토픽에는 `"ops":true`도 들어간다.
- 카메라 마지막 프레임이 3초보다 오래되면 offline이다.

### 2.2 REST (에이전트·LLM 도구용)

| 주소 | 내용 |
|---|---|
| `GET /v1/occupancy` | 위 occupancy 필드 + `confidence`(0~1, 센 사람들의 검출 신뢰도 평균), `age_s`(지금 − ts, 초), `fps`, `infer_ms`, `camera{online, age_s, reconnects}` |
| `GET /v1/proximity` | 위 proximity 필드 + `people[]`(사람별 거리), `confidence`(몸통 영역 유효 비율), `skew_ms`(두 웹캠 프레임 시각 차), `age_s`, `cameras{left, right}` |
| `GET /v1/health` | `status`, `uptime_s`, `ops`, `mqtt`, 카메라 3대 상태, 각 파이프라인 fps |

**사용 규칙(권장)**
- `age_s > 15` 이거나 카메라 `online:false`이면 값을 믿지 말고 "모름"으로 처리한다.
- 특히 0명으로 처리하면 안 된다.
- 빈 방 판정(냉방 끄기)은 count = 0이 5분 연속일 때만 한다.

## 3. 자원 계획 (계산치 vs 실측치)

- 측정 조건: Jetson Orin Nano Super, 호스트 실행(venv), 실내 조명
- 측정 도구: tegrastats 60초 평균. jtop은 설치되어 있지 않고 설치에 sudo가 필요해서 tegrastats를 썼다.

| 항목 | 계산 | 실측 | 차이 이유 |
|---|---|---|---|
| A1 GPU | 5 fps × 타일 4장 × ~9 ms ≈ 18% | infer_ms 67~97 ms/프레임(타일 4장, 전후처리 포함) | 전처리·NMS는 CPU라 GPU 시간은 이보다 작음 |
| A4 GPU | 8 fps × ~5 ms ≈ 4% | 7.9~8.0 fps 유지 | — |
| GPU 합계 | 22% (A1 10 fps면 40%) | 60초 시험 평균 15%, **12시간 평균 41.1%** (p95 99%) | 계산(22%)보다 높다. 타일 4장 배치·전처리 리사이즈·NMS 일부가 GPU에서 돌고, 엔진 실행 시간이 1장 9 ms 가정보다 길다(추론 평균 68.6 ms/프레임). 짧은 측정은 대표성이 없었다 |
| CPU | SGBM 코어 1개의 25~60% + RTSP 디코딩 | **평균 64%** (전체) | 2560x1440 H.264 디코딩과 SGBM, 웹캠 MJPEG 디코딩 2개 |
| 서비스 메모리 | 엔진 2개 + 버퍼 ≈ 0.7~0.9 GB | **RSS 1.88~2.09 GB** | torch·CUDA 컨텍스트 자체가 1 GB 이상 |
| 보드 RAM | — | 2.88 GB / 7.49 GB (재부팅 뒤), 4.29 GB (재부팅 전, 다른 프로그램 포함) | |
| LLM 추가 | +0.5~1.9 GB | 운영에서 제외 | 남는 RAM 3~4.5 GB라 작은 모델은 가능하지만, GPU를 독점하는 시간 문제(6-1)로 이번 운영에서는 뺐다 |
| 전력 | — | **10.3~11.6 W** | |
| 온도 | — | Tj 58 ℃ | |

12시간 평균은 6절에 있다. 12시간 기준 RAM 평균 3.12 GB(최대 3.27 GB), 전력 평균 9.89 W(최대 11.22 W), Tj 평균 57.4 ℃(최대 59.2 ℃).

**정리**
- GPU는 여유가 있다.
- 먼저 바닥나는 것은 **CPU(디코딩 + SGBM)** 와 **메모리(LLM을 올릴 때)** 다.

## 생각해 볼 점

**세 가지 주기를 다르게 둔 이유는?**
- 재실 인원은 10초마다 보낸다. 천천히 변하는 값이고, 냉난방·CO₂ 제어는 분 단위로 반응하므로 10초면 충분하다. 주기 발행이 하트비트 역할도 한다.
- 통행 이벤트는 즉시 보낸다. 한 번 생기고 끝나는 사건이라 모아서 보내면 순서와 시각이 흐려진다.
- 거리 알람은 상태가 바뀔 때만 보낸다. 받는 쪽(경고등)은 "지금 near인가"만 알면 되고, retain이 현재 상태를 보존한다.
- 알람을 매 프레임 보내면 문제가 생긴다.
  - 8 fps면 초당 8건, 하루 70만 건이 된다. 브로커·네트워크·구독자가 쓸데없는 부하를 받는다.
  - 경계 근처에서 near/mid가 깜빡이면 경고등이 깜빡이고 알림이 폭주한다. 실제로 hold를 넣기 전에 1~2초마다 바뀌었다.
  - 진짜 상태 변화가 소음에 묻힌다.

**LLM이 이 서비스를 도구로 쓰려면 ts 외에 무엇이 더 있어야 하나?**
- **얼마나 오래된 값인가:** `age_s`, 그리고 카메라 `online`과 마지막 프레임 나이. ts만 있으면 LLM이 시계를 비교해야 하는데, 잘 못한다.
- **얼마나 믿을 만한가:** `confidence`, 평활 창(`window_s`), 측정 불가일 때 `state: unknown`과 `reason`. 예를 들어 "웹캠 끊김"과 "사람 없음"은 다르다.
- **단위와 범위:** `near_m`·`far_m`, `capacity`, 구역 이름. 숫자만 주면 LLM이 단위를 추측한다.
- 그래서 REST 응답에 이 필드들을 모두 넣었다.

**카메라를 추가하면 어느 자원이 먼저 바닥나나?**
- 우리 실측으로는 **CPU와 GPU가 비슷하게** 먼저 찬다. 60초 시험에서 CPU 평균 64%였고, 12시간 GPU 평균은 41%, 타일 추론 때는 순간 99%였다.
  - 2560x1440 RTSP 디코딩, 웹캠 MJPEG 디코딩 2개, SGBM이 모두 CPU에서 돈다.
  - 하드웨어 디코더(NVDEC/NVJPG)를 쓰거나 stream2(저해상도)를 쓰면 줄일 수 있다.
- 다음은 **메모리**다. 서비스 하나가 2 GB이고, LLM을 함께 올리면 7.5 GB 중 여유가 빠듯해진다.
- **USB 대역폭·허브:** 웹캠 하나를 다시 꽂을 때 같은 허브의 다른 웹캠도 끊겼다. 웹캠을 더 늘리면 USB 컨트롤러를 나눠야 한다.
- **GPU**는 고해상도 카메라를 여러 대 2x2 타일로 돌릴 때 비로소 문제가 된다.

## 확인 문제 6

**6-1.**
- GPU 계산: 재실 1회/s × 10 ms = 1%, 통행 15 × 5 ms = 7.5%, 거리 15 × 5 ms = 7.5% → **약 16%**.
- SGBM 15 × 20 ms = 30%는 CPU 코어 하나 몫이라 GPU에는 들어가지 않는다.
- LLM이 질의마다 2초씩 GPU를 쓰면, 그 2초 동안 검출 커널이 줄을 서서 기다린다.
  - 프레임이 밀리고 fps가 떨어지며 결과의 `age_s`가 커진다.
  - 가장 위험한 것은 **거리 알람이 최대 2초 늦어지는 것**이다.
- 완화 방법:
  - 알람 경로를 우선 처리한다. 비전 처리를 높은 우선순위 CUDA 스트림에 두거나, LLM 실행 중에는 재실 인원 fps만 낮춘다.
  - LLM은 작은 모델과 짧은 출력으로 제한하고, 질의 빈도를 제한한다.
  - LLM은 숫자 API(REST)만 부르게 해서 영상 처리를 다시 시키지 않는다.
  - 받는 쪽은 `age_s`로 오래된 값을 걸러 낸다.

**6-2.**
- `ExecStartPre=` 지시어를 쓴다.
- 우리 `usb_setup.sh`에 넣은 명령의 요지는 다음과 같다(제어 이름은 드라이버 버전에 따라 다를 수 있음).
  ```
  D=/dev/v4l/by-path/platform-3610000.usb-usb-0:2.4:1.0-video-index0
  v4l2-ctl -d $D -c focus_automatic_continuous=0 -c power_line_frequency=2
  v4l2-ctl -d $D -c focus_absolute=0   # AF 끈 뒤 따로 보내야 I/O error 없음
  v4l2-ctl -d $D -c auto_exposure=1 -c exposure_time_absolute=60
  ```
  (2.2도 같게 한다.)
- 장치 이름은 재부팅마다 번호가 바뀌므로 by-path로 지정한다.
- 설정이 실패해도 서비스는 시작되게 하려면 `ExecStartPre=-...`처럼 앞에 `-`를 붙인다.

**6-3.**
1. **포트를 나눈다:** 프로그램마다 `--port`를 다르게 주고 문서화한다. 우리는 팀원 8011, 뷰어 8020, 서비스 8030으로 나눴다.
2. **한 프로세스로 합친다:** 한 서버가 경로(`/v1/occupancy`, `/v1/proximity`)로 나눠 제공한다. 우리 t6 서비스가 A1과 A4를 한 포트로 합친 방식이다. 리버스 프록시 하나 뒤에 여러 앱을 두는 것도 같은 방법이다.
- 덧붙여, 두 번째가 죽었을 때 systemd가 계속 재시작하며 같은 오류를 반복하지 않도록 포트 충돌은 시작 전에 점검한다.

**6-4.** 영상이 보드 밖으로 나가는 경로와 운영 모드 대책이다.

| 경로 | 운영 모드 대책 |
|---|---|
| 뷰어 (MJPEG/HTTP 화면) | 운영 서비스에는 화면 엔드포인트가 없다. 뷰어 프로그램은 띄우지 않는다 |
| RTSP 재송출 | MediaMTX는 127.0.0.1 전용이고 운영 중에는 실행하지 않는다 |
| 스냅샷 | `--snap-every 0`. 운영 서비스에는 저장 코드 자체가 없다 |
| 녹화 | VideoWriter 없음 |
| 크롭 (학습·평가용) | 평가 때만 젯슨 안에 저장하고 평가 뒤 삭제한다 (과제 3: 375장 삭제) |
| 로그 | 숫자만 남긴다. 이미지 경로·base64를 넣지 않는다 |
| MQTT/REST 페이로드 | 숫자·상태만 보낸다 |
| 사람이 직접 복사 (scp, 공유 폴더) | 팀 공유 폴더에서 사진 제외 |
| 카메라 자체 (IP 카메라 웹 화면, SD·클라우드 녹화) | 젯슨 직결 랜선으로만 연결한다. 카메라 녹화 설정은 꺼져 있는지 확인이 필요하다 |

- 증명: 12시간 동안 새 이미지 파일 수를 1분마다 셌다.

**6-5.**
- 제어 로직은 **count**를 써야 한다. 10초 median으로 평활한 값이라, 한 프레임 놓침이나 오검출에 흔들리지 않는다.
- **raw**를 남겨 두는 이유는 다음과 같다.
  1. 평활 창을 바꿔 다시 계산하거나 count와 raw 차이로 흔들림 정도를 진단할 수 있다.
  2. 정답과 비교해 검출기 자체의 오차를 따로 평가할 수 있다. 과제 3에서 raw와 창별 MAE를 비교했다.
  3. 빠른 반응이 필요한 소비자는 직접 다른 평활을 적용할 수 있다.
